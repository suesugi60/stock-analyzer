# TikTok配信用ビンゴ 設計書

作成日: 2026-11-13

## 目的

TikTokのライブ配信中に、主催者(配信者)とリスナーがビンゴで遊ぶためのWebアプリ。
狙いはリスナーとの交流を深めること。

- リスナーはURLを開くだけで参加できる(登録・インストール不要)。
- カードは、リスナーが枚数を申請し、主催者が許可した分だけ配られる。
- 主催者が配信中に番号を発表すると、全員のカードが連動して動く。

本リポジトリ(stock-analyzer)は株式分析ツールだが、スゴロクと同じく `bingo/` サブフォルダに同居させる。
既存コード(株式分析・スゴロク)とは一切共有しない。

## 利用者と合意したこと

| 項目 | 決定 |
|---|---|
| 流れ | リスナーがURLを開く → 名前と希望枚数を申請 → 主催者が許可 → 許可された枚数のカードが届く |
| 参加 | URLを知っていれば誰でも申請できる |
| 配布 | 主催者が許可するまでカードは配られない。1人何枚でも配れる。枚数はリスナーからの申請 |
| 番号 | 配信中に主催者が番号を発表し、それに連動してサイトが動く |
| 作り方 | Cloudflare(下記「作り方の候補」のA案) |

利用者が了承済みの「できないこと」:

1. 本人確認はしない。名前は自己申告。
2. TikTokのコメント・ギフトとは自動連動しない。許可は主催者の手作業。
3. ライブのコメントに貼ったURLはタップできない。URLの案内は主催者が工夫する。
4. URLを知っていれば、申請を送ること自体は誰でもできる。
5. サーバーが必要(スゴロクのようなファイル1つの構成にはできない)。
6. ギフトと景品を組み合わせる場合の規約・法律の確認は主催者が行う。

## 作成者の判断(利用者が明示していないもの)

以下は作成者が決めた。利用者の要望で変えてよい。

| 項目 | 判断 | 理由 |
|---|---|---|
| 番号の出し方 | 「ランダムに引く」ボタンと、1〜75の盤面をタップして発表する方法の両方 | アプリに引かせる配信も、手元の抽選機で引く配信もできる |
| 穴あけ | 自動。リスナーは操作しない | リスナーは主に配信を見ているため |
| 申請の項目 | 名前と希望枚数のみ(合言葉での照合はなし) | 「できないことはそのままでよい」との回答 |
| カード | 5×5、数字は1〜75、中央はFREE。列ごとの範囲は B 1–15 / I 16–30 / N 31–45 / G 46–60 / O 61–75 | 最も一般的な形式 |
| 1回の申請の上限 | 50枚。許可後に何度でも追加申請できる(1人の合計に上限なし) | 入力ミスや荒らしで極端な枚数が出るのを防ぐ |
| 主催者による枚数変更 | 許可のときに1〜50枚の範囲で変えられる | 申請どおりに配らない場面に対応 |
| 途中参加 | 受付中ならゲーム途中でも申請・配布できる。発表済みの番号は配布時点で穴が開く | 配信の途中から来る人がいる |
| ビンゴの扱い | 最初のビンゴが出てもゲームは続く。達成順の一覧を出す | いつ終えるかは主催者が決める |
| ビンゴの一覧 | 主催者と全リスナーに見える(名前・何個目の番号で達成したか) | 盛り上がりのため |
| 部屋 | 常に1つ。URLは固定で、主催者がリセットして繰り返し使う | プロフィールに固定のURLを置ける |
| 次のゲーム | 「番号だけリセット(カードはそのまま)」と「すべてリセット」の2種類 | 同じメンバーで続ける場合と仕切り直す場合がある |
| 主催者の認証 | 合言葉(パスワード)1つ。Cloudflareのシークレットに設定 | アカウントの仕組みを作らずに済む |
| 見た目 | 明るくポップ。スマホ縦持ち優先 | スゴロクと同じ系統。実物を見てから調整する |
| 音 | 出さない | リスナーは配信の音を聞いている |
| 言語 | 日本語のみ | |

## ゴール・やらないこと・避けたい失敗

### ゴール

- 配信中に止まらない。同時500人・合計5,000枚まで問題なく動く。
- リスナーがTikTokとブラウザを行き来しても、カードが消えず、戻った瞬間に最新の状態になる。
- 番号の発表から全員の画面への反映まで、通常1秒以内。
- 主催者はスマホでもPCでも操作できる。

### やらないこと

- TikTokとの自動連動(コメント・ギフトの読み取り、TikTokログイン)。
- 本人確認。
- 複数の部屋の同時開催。
- 景品や当選者の管理。
- 配信画面に映すための専用表示(OBS用オーバーレイ)。
- 音、チャット、多言語対応。
- カードの大きさや数字の範囲の変更。

### 避けたい失敗(動いていても失敗とみなす)

- 許可していないのにカードが配られる。
- 主催者以外が、番号の発表・許可・リセットをできる。
- リスナーがカードの中身や穴の状態を偽れる。
- アプリを切り替えたり再読み込みしたりしただけでカードが消える。
- 主催者の押し間違いでゲームが壊れる(リセットや取り消しに確認がない)。
- リスナーが入力した名前によって、主催者画面で不正なスクリプトが動く。

## 作り方の候補

| | A. Cloudflare(採用) | B. Firebase | C. Streamlit Community Cloud |
|---|---|---|---|
| 新しく必要なもの | Cloudflareの無料アカウントとGitHub連携 | Googleアカウントでの初期設定 | なし(株アプリと同じ場所) |
| 人数 | 数百人でも無料枠に収まる見込み | Realtime Databaseは同時100接続まで。Firestoreは読み取り1日5万回まで | 公式の上限は非公開。数十人を超えると重くなるおそれ |
| 反映 | ほぼ即時(WebSocket) | ほぼ即時 | 数秒遅れる(定期的な再読み込み) |
| 配信前の準備 | 不要 | 不要 | 12時間アクセスがないと休止するため毎回起こす |
| 動作確認 | 開発環境で全体を動かせる | 本番の設定は確認しきれない | 確認できる |

Aを採用した理由: 配信中に止まるのが最も困るため、人数の余裕が大きく、渡す前に全体を動かして確認できる点を重視した。
Bは無料枠を超えるとその場で止まる。Cは手間が最小だが、人数が増えたときの動きが読めず、見た目も簡素になる。
利用者はAを選んだ。

## 全体構成

Cloudflare Workers 1つで、ページの配信とリアルタイム同期の両方を担う。

- 静的ファイル(Workers Static Assets): リスナー画面と主催者画面。
- Durable Object `BingoRoom`(1個だけ): 部屋の状態を持ち、全員とWebSocketでつながる。
  状態はDurable Object内蔵のSQLiteに保存する。無料プランで使えるのはSQLite方式のみ。
- 番号の抽選・カードの生成・ビンゴの判定はすべてサーバー側で行う。

```
bingo/
  README.md          遊び方・公開手順・上限・テスト方法
  package.json       wrangler(開発用)とテスト用スクリプト
  wrangler.jsonc     Cloudflareの設定
  src/
    index.mjs        入口。/ws をDurable Objectへ渡す
    room.mjs         BingoRoom(状態・通信・権限の確認)
  public/
    index.html       リスナー画面
    host.html        主催者画面
    logic.mjs        純粋関数(カード生成・列の判定)。サーバーとブラウザで共用
    (CSS・画面用スクリプトは実装者が分ける)
  test/
    logic.test.mjs   純粋関数のテスト
    room.test.mjs    サーバーのテスト(ローカルのwrangler devにWebSocketで接続)
    e2e.test.mjs     画面のテスト(Playwright)
```

ビルド工程は置かない(フレームワークなし、素のHTML・CSS・JavaScript)。

開発環境(Node 22、wrangler 4.161.0)で、静的ファイルの配信・SQLite方式のDurable Object・
WebSocketの一斉送信がローカルで動くことは確認済み。

## ルール

### 申請と配布

- リスナーは端末ごとに1人として扱う。初回にブラウザが秘密の合い札(ランダムな文字列)を作って保存し、
  以後それを使って自分のカードを取り戻す。サーバーは合い札のハッシュだけを保存する。
- 名前は1〜20文字(前後の空白と制御文字は除く)。カードを1枚でも持ったら変えられない。それまでは申請のたびに変えられる。
- 枚数は1〜50の整数。
- 申請中にできる申請は1人1件まで。取り消すか、許可・却下されたら次を出せる。
- 受付を締め切ると新しい申請は受け付けない。すでに届いている申請は、締め切り後も許可・却下できる。
- 許可すると、サーバーがその枚数のカードを作り、その人にだけ送る。
- 他人のカードの中身はリスナーに送らない。

### 番号

- ランダムに引く: サーバーが、まだ出ていない番号から均等に1つ選ぶ。
- 盤面から発表: 主催者が選んだ番号を発表する。すでに出ている番号は無視する。
- 取り消せるのは直前の1つだけ。取り消すと、その番号で成立したビンゴも取り消される。
- 75個すべて出たら「ランダムに引く」は押せない。
- 乱数は暗号用の乱数源を使う。テストでは乱数を差し替えられるようにする。

### ビンゴの判定

- 列は縦5・横5・斜め2の12本。FREEは最初から開いている。
- カードごとに、最初に1列そろった時点の「何個目の番号か」を記録する。
- 一覧はその順に並べる。同じ番号で同時にそろったカードは同順位。
- 配った時点ですでにそろっていたカードは、その時点の最新の番号で達成したものとして扱う。
- 2列目以降は順位に影響しない。カードには何列そろったかを表示する。

### ブロック

- ブロックすると、その人の申請中の申請は却下、カードは削除、以後の申請は受け付けない。ビンゴの一覧からも外れる。
- 解除できる(カードは戻らない)。
- 端末単位なので、ブラウザのデータを消せば別人として申請し直せる。そこは主催者の許可で止める。

### リセット

- 次のゲーム(カードはそのまま): 発表済みの番号とビンゴの記録を消す。カード・参加者・申請は残す。
- すべてリセット: 番号・カード・申請・参加者・ブロックをすべて消す。リスナーは未申請に戻る。受付の状態は変えない。

## 通信

- WebSocketでJSONをやりとりする。メッセージの形は実装者が決める。
- 接続したら、リスナーは合い札を、主催者は合言葉を最初に送る。サーバーは接続ごとに役割を覚え、
  主催者用の操作は主催者の接続からしか受け付けない。
- 番号の発表は、全員に小さなメッセージ(番号と何個目か)を送る。全状態の再送はしない。
- リスナーには、共通の情報(受付中か、発表済みの番号、ビンゴした人)と、その人自身の情報(名前、申請、カード)だけを送る。
- 主催者には、申請・参加者・ビンゴの一覧を送る。
- WebSocket Hibernation APIを使い、やりとりがない間はDurable Objectを休ませる。
  そのため、メモリに置いた情報は消える前提で、必要な状態はすべてSQLiteに置く。
- 再接続: 切断されたら間隔を空けながら自動でつなぎ直す。画面が再び表示されたとき(アプリの切り替えから戻ったとき)は、
  すぐに接続を確かめ、最新の状態をまるごと取り直す。取り直しは何度行っても結果が変わらないこと。

## データ

Durable ObjectのSQLiteに置く。表の形は実装者が決めてよいが、次を保存する。

- 受付中かどうか。
- 参加者: ID、合い札のハッシュ、名前、ブロックの有無。
- 申請: 誰が、何枚、状態(申請中・許可・却下・取り消し)、実際に配った枚数、届いた順。
- カード: 誰の、何番目の、25マスの数字(FREEは0)、ビンゴを達成したのが何個目の番号か。
- 発表済みの番号と順番。

個人情報は自己申告の名前だけ。Cookieや追跡は使わない。

## セキュリティ

- 主催者の合言葉はCloudflareのシークレット `HOST_PASSWORD` に置く。リポジトリには入れない。
  設定されていない場合、主催者としては誰も入れない。
- 合言葉の総当たり対策として、失敗が続いた接続元からの試行を一定時間止める。
- リスナーからの入力はすべてサーバーで検証する(型、範囲、長さ)。大きすぎるメッセージや、短時間に多すぎるメッセージを送る接続は切る。
- リスナーが入力した名前は、画面では必ず文字として表示する(HTMLとして解釈させない)。主催者画面でも同じ。
- 画面にはContent-Security-Policyを付け、外部のスクリプトを読み込まない。
- カードと穴の状態はサーバーが決める。ブラウザ側の表示を書き換えても、主催者画面の判定は変わらない。

## 上限と無料枠

サーバーで強制する上限:

| 項目 | 上限 | 超えたとき |
|---|---|---|
| 名前 | 20文字 | 申請を受け付けない |
| 1回の申請 | 50枚 | 申請を受け付けない |
| 部屋全体のカード | 5,000枚 | 許可できない旨を主催者に表示 |
| 申請中の申請 | 1,000件 | 新しい申請を「混み合っています」で断る |

Cloudflare無料プランの上限(2026年11月時点の公式ドキュメント):

- Workersへのリクエスト: 1日10万回。
- Durable Objectへのリクエスト: 1日10万回(WebSocketの接続1回が1回、受信メッセージは20通で1回)。
- Durable Objectの稼働時間: 1日13,000 GB秒。休んでいる間は数えない。
- SQLite: 1日あたり読み取り500万行、書き込み10万行。
- 超えるとその種類の操作がエラーになり、日本時間の午前9時にリセットされる。

リスナーがアプリを切り替えて戻るたびに再接続が1回起きる。500人が1配信で75回ずつ戻ると約3.8万回で、上限内に収まる。
これを超える規模になったら有料プラン(月5ドル)に切り替える。READMEに書く。

## 公開手順(利用者の作業)

READMEに画面ごとの手順を書く。手順は実装時に最新の公式ドキュメントで確かめてから書く。

1. このブランチを `main` に取り込む。
2. Cloudflareの無料アカウントを作る。
3. Workers & Pages でGitHubのリポジトリ `suesugi60/stock-analyzer` を取り込む。ルートディレクトリは `bingo`。
   以後、`main` への反映で自動的に公開される。
4. シークレット `HOST_PASSWORD` に合言葉を設定する。
5. 表示されたURL(`bingo.○○.workers.dev`)を開いて確認する。

作成者はCloudflareのアカウントを持たないため、本番への公開そのものは試せない。
ローカルでの動作確認までを行い、最初の公開で問題が出たら利用者と一緒に直す。

### 配布上の注意

`publish_public.sh` はDropbox側の元フォルダから `rsync --delete` で公開リポジトリへ同期する。
GitHub側にだけ `bingo/` があると、次回の同期で削除される。Cloudflareは `main` の内容をそのまま公開するため、
削除されると次の自動公開が失敗する。元フォルダにも `bingo/` と `docs/` をコピーしておくこと(READMEにも書く)。
